## Summary

Phase 9 closes out v1.2 by hardening every cross-cutting integration that real users hit on the Triton backend. The implementation surface is **small** (3 new test files, 2 new helpers in `_ops.py`, 1 new top-level function, 1 helper script, 1 routing-table JSON, README + CHANGELOG additions) but the **landmine surface is large** — 6 distinct ways this phase can ship a green-CI build that breaks for users:

1. The legacy `Butterfly` nn.Module **does not call `_ops.butterfly_multiply` at all** — it imports `butterfly_multiply` from `torch_structured.butterfly.multiply`, which calls `torch.ops.torch_structured.butterfly_multiply(...)` (the C++ op registered by `csrc/butterfly.cpp`). Under `BACKEND=triton`, the nn.Module STILL goes to the C++ path because the import is resolved at module-load time, not via `_ops` attribute access. **This is the #1 landmine; all `torch.compile` / FSDP / DDP / checkpoint tests must explicitly call `torch_structured._ops.butterfly_multiply` OR the planner must add a routing shim in `torch_structured.butterfly.multiply.butterfly_multiply` that re-reads `_ops`.** See §0.
2. PyTorch 2.6's FSDP API has TWO co-existing classes — `FullyShardedDataParallel` (FSDP1, has `ignored_modules`) and `fully_shard` (FSDP2, does NOT have `ignored_params` in 2.6 — added later). Plan must target FSDP1 for the `twiddle` no-shard hint. See §1.
3. The 260419-p27 fake-tensor bug is fixed by `register_fake` — already wired in `_triton/butterfly/op.py:1577-1597`. The Phase 9 test must exercise the **full nn.Module surface** under `FakeTensorMode`, not just the raw `triton_op` (which Phase 4's `test_dispatch.py` already covers). See §3 and §0.
4. `triton.testing.do_bench` returns **milliseconds** (not seconds) and **does NOT call `torch.cuda.synchronize` itself** — it uses an internal device-interface sync. For backward bench, pass `grad_to_none=[twiddle, input_]` to prevent grad accumulation across iterations. See §5.
5. The complex64 conjugate sign flip is **the** load-bearing complex-correctness detector — already caught by Phase 8 D-50c. Phase 9 inherits the warning; do not loosen tolerances on complex64 d_twiddle. See §4.
6. `torch_structured.butterfly.multiply.butterfly_multiply_fw` / `butterfly_multiply_bw` are `@torch.jit.script`-decorated — they cannot be monkey-patched directly after JIT. Phase 8's SC#4 test (`test_butterfly_backward_no_cpp_symbol`) monkey-patches via the **module attribute**, not the jit-scripted function — already correctly done at `tests/test_butterfly_triton.py:705-774`. Phase 9 does NOT change this mechanism — only the test cell selection (D-61a). See §8.

**Primary recommendation:** Before writing any Phase 9 plans, resolve landmine #1 — decide whether `torch_structured.butterfly.multiply.butterfly_multiply` is rewritten to delegate to `torch_structured._ops.butterfly_multiply` (changes the legacy module behavior under `BACKEND=triton`), OR all Phase 9 nn.Module-surface tests build models that have been explicitly rebound. Without this decision, the entire `torch.compile` / FSDP / DDP / checkpoint suite verifies nothing useful — it tests the C++ path under `BACKEND=triton`.

## §0. CRITICAL LANDMINE — nn.Module surface does not route through `_ops`

**Files involved:**
- `torch_structured/butterfly/multiply.py:27-30` — top-level `butterfly_multiply` calls `torch.ops.torch_structured.butterfly_multiply` (the C++ op from `csrc/butterfly.cpp`) DIRECTLY.
- `torch_structured/butterfly/butterfly.py:8` — `from .multiply import butterfly_multiply` — binds `butterfly_multiply` to the C++ wrapper at module-load time, NOT to `_ops.butterfly_multiply`.
- `torch_structured/butterfly/butterfly.py:124,128,239,243` — call sites inside `Butterfly.forward` / `ButterflyBmm.forward` use the local-binding `butterfly_multiply`, which is the C++ wrapper.

**Consequence under `BACKEND=triton`:**
```python
torch_structured.set_backend("triton")
# _ops.butterfly_multiply is rebound to the Triton kernel — GOOD.
m = Butterfly(256, 256).cuda()
m(x)  # routes through torch_structured.butterfly.multiply.butterfly_multiply
      # which calls torch.ops.torch_structured.butterfly_multiply (C++) — BAD.
```

The `_ops` dispatcher is bypassed for every nn.Module call. Phase 9's `torch.compile(Butterfly(...))` test under `BACKEND=triton` measures the C++ path, not the Triton path.

**Why this hasn't surfaced before:**
- Phase 7+8's `tests/test_butterfly_triton.py` call `torch_structured._ops.butterfly_multiply(...)` DIRECTLY (verified at `tests/test_butterfly_triton.py:67,83,101,119,...`) — never through the nn.Module. The only nn.Module-surface test is `test_butterfly_unitary` at `:365` — but `test_butterfly_unitary` checks the unitary property of the math, not which backend executed.
- Phase 8 SC#4's `test_butterfly_backward_no_cpp_symbol` (`tests/test_butterfly_triton.py:705-774`) does call `torch_structured._ops.butterfly_multiply(twiddle, x, True, n)` directly at `:766` — not through `Butterfly(...)`. So it currently passes BUT does not verify that the nn.Module surface routes via `_ops`.

**Resolution options (planner picks; recommend Option A):**

| Option | Approach | Tradeoff |
|--------|----------|----------|
| **A (recommended)** | Modify `torch_structured/butterfly/multiply.py:27-30`: replace the `@torch.jit.script` shim with a plain delegator: `def butterfly_multiply(*args, **kw): return torch_structured._ops.butterfly_multiply(*args, **kw)`. This makes the nn.Module surface honor `set_backend`. | Adds attribute-access overhead per call (one Python attribute lookup); breaks `@torch.jit.script` of `multiply.py` — but Phase 8 SC#4 already documents that callers should use `_ops` attribute access. Existing tests that import `from torch_structured.butterfly.multiply import butterfly_multiply` keep working — the shim just re-routes. **Requires Phase 9 09-01 task that touches `butterfly/multiply.py`** (not previously in scope — confirm with user). |
| **B** | Keep `multiply.py` untouched. Write Phase 9 09-02 tests so they explicitly call `torch_structured._ops.butterfly_multiply(...)` (e.g., build a thin `nn.Module` test wrapper that uses `_ops` directly). | Tests pass green but ship a USER-VISIBLE BUG: a real user who calls `Butterfly(256, 256)(x)` under `BACKEND=triton` gets the C++ op, not Triton. v1.2's promise (`Triton is the default backend`) is broken at the nn.Module surface — the one users actually touch. **Not recommended.** |
| **C** | Modify the `Butterfly.forward` body in `butterfly/butterfly.py:124,128,239,243` to call `torch_structured._ops.butterfly_multiply(...)` directly. | Cleaner than A in some ways but touches 4 call sites and 2 classes; A is one edit point. |

**Recommended:** Option A — single-point delegator in `butterfly/multiply.py`. The planner should ADD a new task to `09-01` that makes this swap and verifies via a `test_butterfly_nn_module_routes_through_ops` test (instantiate `Butterfly`, call forward, assert via the SC#4 monkey-patch pattern that the C++ op was NOT invoked when `BACKEND=triton`).

## §1. PyTorch 2.6+ FSDP API for excluding `twiddle` from sharding

**Findings:**

PyTorch 2.6 has TWO FSDP APIs that coexist:

**FSDP1 — `torch.distributed.fsdp.FullyShardedDataParallel`** [VERIFIED: pytorch source at `torch/distributed/fsdp/fully_sharded_data_parallel.py`]
- Class-based wrapper; documented signature includes `ignored_modules` AND `ignored_states` (only one may be specified).
- `ignored_modules`: "Modules whose own parameters and child modules' parameters and buffers are ignored by this instance."
- Still fully supported in PyTorch 2.6; no deprecation notice.
- Recommended for projects that need parameter-exclusion granularity in 2.6.

**FSDP2 — `torch.distributed.fsdp.fully_shard`** [VERIFIED: docs.pytorch.org/docs/2.6/distributed.fsdp.fully_shard.html]
- Function-based "composable FSDP" (newer API).
- Signature in PyTorch 2.6: `fully_shard(module, *, mesh=None, reshard_after_forward=True, shard_placement_fn=None, mp_policy=..., offload_policy=...)`
- **CRITICAL:** `ignored_params` is **NOT** a parameter in PyTorch 2.6's `fully_shard` signature. It was added in later versions (the GitHub tracking issue is `pytorch/pytorch#148242`, "Unclear behavior of `ignored_params` in `fully_shard`" — feature exists in main but not in 2.6).
- The 2.6 FSDP2 path has no first-class way to exclude a parameter; the only escape hatches are (1) constructing a custom `shard_placement_fn` that returns a Replicate placement for the twiddle dim (complex), or (2) calling `fully_shard` only on the parent modules that DON'T contain `Butterfly` (manual wrap policy).

**Recommendation for Phase 9 09-02 (PyTorch 2.6 baseline — COMPAT-05):**

Use **FSDP1** with `ignored_modules` — the cleanest 2.6-compatible API:

```python
# tests/test_distributed_triton.py
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

@pytest.mark.multigpu
def test_fsdp_butterfly_smoke():
    """2-GPU FSDP smoke (PyTorch 2.6 — FSDP1 with ignored_modules per D-64b).

    The twiddle parameter is excluded from sharding because Butterfly's
    forward expects the FULL twiddle tensor on each rank (no per-rank slice).
    PyTorch 2.6's fully_shard (FSDP2) lacks ignored_params — we use FSDP1.

    Run via: torchrun --nproc_per_node=2 -m pytest tests/test_distributed_triton.py -m multigpu
    """
    torch.distributed.init_process_group(backend='nccl')  # FSDP requires NCCL for GPU
    rank = torch.distributed.get_rank()
    torch.cuda.set_device(rank)

    m = nn.Sequential(
        Butterfly(256, 256, bias=False),
        nn.Linear(256, 10),
    ).cuda()

    # Exclude ALL Butterfly modules from sharding.
    ignored = [mod for mod in m.modules() if isinstance(mod, Butterfly)]
    m = FSDP(m, ignored_modules=ignored)

    x = torch.randn(8, 256, device='cuda', requires_grad=True)
    loss = m(x).sum()
    loss.backward()
    torch.distributed.barrier()
    torch.distributed.destroy_process_group()
```

**Why NCCL not gloo:** FSDP1 requires a backend that supports GPU collectives; `nccl` is the only production-tested choice. Gloo works for CPU-only DDP but FSDP1's all-gather is NCCL-only in practice. [VERIFIED: pytorch FSDP examples always use `nccl`; the FSDP source at `torch/distributed/fsdp/fully_sharded_data_parallel.py` raises a clear error on non-NCCL on GPU.]

**Forward-compat note for the planner:** Document in the test's docstring that when the project bumps to PyTorch 2.7+, the cleaner FSDP2 path becomes available via `fully_shard(module, ignored_params=set(butterfly.twiddle for ...))`. Phase 9 doesn't ship that; it ships the 2.6-compatible FSDP1 path.

**LANDMINE:** Using `fully_shard` in 2.6 with no exclusion mechanism would silently shard the twiddle across ranks, producing a per-rank `twiddle[shape // world_size, ...]`. Forward then runs with garbage data (every rank has 1/N of the twiddle but expects full). Symptom: loss values diverge across ranks; backward all-gathers a wrong gradient. Detection: assert `loss_rank0 == loss_rank1` at the end of the test (the recommendation already in CONTEXT.md `<specifics>` is correct).

**Sources:**
- [torch.distributed.fsdp.fully_shard (PyTorch 2.6)](https://docs.pytorch.org/docs/2.6/distributed.fsdp.fully_shard.html) [CITED]
- [FullyShardedDataParallel (PyTorch 2.6) — ignored_modules](https://docs.pytorch.org/docs/2.6/fsdp.html) [CITED]

## §2. `torch.compile` graph-break detection idiom

**Findings:**

Three viable detection mechanisms, in increasing order of strictness:

| Mechanism | What it does | Recommended use |
|-----------|--------------|-----------------|
| `torch.compile(fn, fullgraph=True)` | Raises an exception (subclass of `torch._dynamo.exc.Unsupported`) at the FIRST graph break encountered during compilation. Strongest enforcement; recommended by official docs. [VERIFIED: docs.pytorch.org] | **PRIMARY** — use this in Phase 9 09-02. |
| `torch._dynamo.explain(fn, *args)` | Returns a structured object reporting `graph_count`, `graph_break_count`, `break_reasons`. Diagnostic; doesn't raise — useful for debugging which break fired. | DIAGNOSTIC fallback when `fullgraph=True` raises and you need to identify the break source. |
| `torch._dynamo.utils.compile_metrics()` | Counter object; less stable API surface (varies by PyTorch version); not recommended for assertion logic. | NOT recommended — fragile. |

**Recommended Phase 9 09-02 pattern:**

```python
# tests/test_torch_compile_triton.py
import torch

def test_torch_compile_butterfly_fullgraph_no_break(backend):
    """fullgraph=True is the strongest assertion: any graph break raises
    torch._dynamo.exc.Unsupported (or a RuntimeError wrapping it) at
    compile time. Works for both forward (during dynamo tracing) and
    backward (when the compiled graph is invoked under .backward()).
    """
    if backend != "triton":
        pytest.skip("torch.compile no-break gate is only meaningful for the triton path")

    m = Butterfly(in_size=256, out_size=256, bias=False, complex=False).cuda()
    m_compiled = torch.compile(m, fullgraph=True)
    x = torch.randn(8, 256, device='cuda', requires_grad=True)
    # If a graph break occurs anywhere in m_compiled, this raises.
    y = m_compiled(x)
    loss = y.sum()
    loss.backward()  # backward also must not graph-break
    assert x.grad is not None
```

**LANDMINE — `fullgraph=True` does NOT trace backward symbolically.** The forward graph is dynamo-traced; backward is built via `register_autograd` AOT'd into the same graph. If the `_backward` callback in `_triton/butterfly/op.py:1315-...` contains an unhandled Python branch (e.g., the small-N fallback `if log_n <= 1`), dynamo handles this as a graph break at FORWARD trace time — the small-N branch becomes a guard, not a runtime break. **Verification:** test at BOTH small-N (`in_size=16`, `log_n=4` is the smallest dense-tier case) AND large-N (`in_size=256`, `log_n=8`) to exercise both branches.

**Why `fullgraph=True` alone is sufficient (per docs):** Per [docs.pytorch.org/docs/stable/user_guide/torch_compiler/compile/programming_model.fullgraph_true.html](https://docs.pytorch.org/docs/stable/user_guide/torch_compiler/compile/programming_model.fullgraph_true.html), `fullgraph=True` is the official enforcement mechanism for "no graph breaks anywhere" — eliminates the need for `compile_metrics()` introspection in 99% of cases.

**`torch._dynamo.config.suppress_errors`:** Default is False. CONTEXT.md says "asserts no graph breaks via `torch._dynamo.config.suppress_errors=False`" — but `suppress_errors=False` is the DEFAULT. Setting it explicitly is belt-and-braces; harmless. The actual gate is `fullgraph=True`.

**Sources:**
- [torch.compile fullgraph=True documentation](https://docs.pytorch.org/docs/stable/compile/programming_model.fullgraph_true.html) [CITED]
- [torch._dynamo.exc.Unsupported issue thread](https://github.com/pytorch/pytorch/issues/135439) [CITED]
- [`CompileProfiler` reports graph breaks while `dynamo.explain` reports no graph breaks #113443](https://github.com/pytorch/pytorch/issues/113443) [CITED — known divergence between mechanisms; fullgraph=True is the canonical one]

Phase 4 wired this for the demonstrator op. ## §4. Deterministic mode composition with `torch.use_deterministic_algorithms()`

**Findings:**

PyTorch's determinism toggles:
- `torch.use_deterministic_algorithms(True)` — sets a global flag; ops that have non-deterministic-only implementations raise `RuntimeError` (warn-only mode available via `warn_only=True`).
- `torch.are_deterministic_algorithms_enabled()` — reader; returns the global flag.
- `torch.utils.deterministic.fill_uninitialized_memory` — separate knob (fills `torch.empty` with NaN; useful for catching uninitialized-read bugs).
- Environment: `CUBLAS_WORKSPACE_CONFIG=:4096:8` or `:16:8` required for some CUDA matmul/bmm under deterministic mode (CUDA 10.2+).

**Recommended composition pattern for `torch_structured.set_deterministic(True)`:**

D-63b locks the composition: HONOR BOTH `_DETERMINISTIC` AND `torch.are_deterministic_algorithms_enabled()`. The library's flag does NOT set PyTorch's global flag — users opt into PyTorch's global determinism separately. `set_deterministic` is **additive scope, not propagating**.

```python
# torch_structured/_ops.py (new, per D-63)
_DETERMINISTIC: bool = False

def set_deterministic(value: bool) -> bool:
    """Toggle deterministic-mode for torch_structured Triton kernels.

    Returns the previous value (save/restore pattern, mirrors set_backend).

    Under deterministic mode, butterfly_multiply backward routes through
    butterfly_multiply_torch (the pure-PyTorch oracle) — slower but
    deterministic because there is no atomicAdd reduction. Forward path
    is unaffected (no atomicAdd in forward; deterministic-by-construction
    via the multi-launch tile structure).

    Composes additively with torch.use_deterministic_algorithms(True):
    deterministic path is active when EITHER flag is True.
    """
    global _DETERMINISTIC
    prev = _DETERMINISTIC
    _DETERMINISTIC = bool(value)
    return prev


def _is_deterministic_mode_active() -> bool:
    """Helper used by _backward in _triton/butterfly/op.py."""
    return _DETERMINISTIC or torch.are_deterministic_algorithms_enabled()
```

## §6. `torch.utils.checkpoint.checkpoint(use_reentrant=False)` interaction with Phase 8's backward

**Findings:**

`torch.utils.checkpoint.checkpoint(use_reentrant=False)` is the modern recommended path (reentrant is deprecated). It DOES work with custom autograd registered via `register_autograd` — but with a known interaction: the checkpoint recomputes the forward during backward, AND the custom autograd's `_backward` ALSO recomputes the forward into the trail buffer (Phase 8 D-49). Net effect: 2× forward recompute.

**Is this correct?** Yes. The user's `checkpoint(forward)` says "don't save activations from forward — recompute during backward." That gives `output_grad` to the saved-tensor pack-hook chain. The `register_autograd` `_backward` callback then receives `grad_out` and proceeds with Phase 8's recompute-into-trail. The two recomputes are independent: checkpoint's recompute reconstructs the forward output (and re-saves `(twiddle, input)` via `_setup_context`); Phase 8's `_backward` then re-runs the forward stage-group launches AGAIN to materialize the per-stage trail.

**Performance: 3× total forward work per backward** (1 forward + 2 recomputes). Memory: ~0 extra activation cache (the user's intent); plus the trail buffer (Phase 8's per-call ~22MB at log_n=11/batch=64).

**Correctness:** Both recomputes are deterministic-by-construction (Phase 7 forward kernel does NOT use atomicAdd — only the backward d_twiddle atomic). So both recomputes yield bit-identical outputs. Gradients are correct.

**Known bug to watch for (#121966):** `torch.compile + torch.utils.checkpoint.checkpoint(use_reentrant=False)` has a known compatibility issue around CUDA RNG state in the recompute. This is upstream PyTorch — not specific to torch_structured. Phase 9's `test_gradient_checkpointing_butterfly` should NOT also be `torch.compile`'d (CONTEXT.md doesn't ask for the cross-product, so this naturally avoids the issue).

**Recommended tolerance for the gradient checkpoint test:**

CONTEXT.md proposes `rtol=1e-4, atol=1e-5`. **This is appropriate but worth justifying:**
- The recompute path is identical mathematically — no atomicAdd reordering between recomputes (Phase 7 forward has no atomicAdd in forward).
- Bit-identity is theoretically achievable IF the kernel's launch order across the two recomputes is identical. `torch.utils.checkpoint` reseeds the RNG state to ensure reproducibility (when `preserve_rng_state=True`, the default).
- So gradients SHOULD be within `rtol=1e-7, atol=1e-7` of the non-checkpointed reference — `1e-4 / 1e-5` is a 1000× safety margin against any inadvertent non-determinism.
- **Recommend:** `rtol=1e-5, atol=1e-6` (Phase 7+8 fp32 d_input envelope), tightening if it passes, loosening to `rtol=1e-4, atol=1e-5` only if there's an unexplained mismatch.

## §7. Checkpoint round-trip with v1.0/v1.1 twiddle layout

**Findings:**

The twiddle layout `(nstacks, nblocks, log_n, n/2, 2, 2)` is documented at:
- `torch_structured/_torch_ref/butterfly.py:17` — `assert twiddle.shape == (nstacks, nblocks, log_n, n // 2, 2, 2)` — the oracle.
- `torch_structured/butterfly/butterfly.py` — `Butterfly.__init__` constructs `self.twiddle = nn.Parameter(torch.empty(twiddle_shape))` with this exact shape.
- v1.0 and v1.1 stored checkpoints have this EXACT shape (verified by reading the `Butterfly` constructor — layout has not changed since Phase 1).

**Complex64 layout:** `torch.complex64` twiddles use the same logical shape `(nstacks, nblocks, log_n, n/2, 2, 2)` but with `dtype=torch.complex64`. Under `view_as_real`, this aliases to `(nstacks, nblocks, log_n, n/2, 2, 2, 2)` — the extra trailing 2 is re/im. v1.0/v1.1 checkpoints with complex64 store the `complex64` dtype directly; `load_state_dict` preserves dtype.

## §8. Runtime selector logging + idempotency

**Findings:**

Python's `logging.info(...)` is **NOT visible** under default pytest output. Default pytest captures stdout AND swallows `logging` below `WARNING`. To see `INFO` messages: `pytest --log-cli-level=INFO` or `-s` (capture-disable) + `caplog` fixture.

**Recommended pattern for once-per-process logging:**

```python
# torch_structured/_ops.py — new
_routing_log_emitted: set[tuple[str, int, str, str]] = set()

def _should_route_to_cuda(op_name: str, shape: tuple, dtype: torch.dtype, direction: str) -> bool:
    """Consult static routing table; True iff Triton ratio > 1.67× CUDA at this cell.

    The routing table is loaded once at module-import time from
    torch_structured/_routing.json. Test-time override via _DISABLE_ROUTING.
    """
    if _ROUTING_DISABLED:
        return False
    log_n = _shape_to_log_n(shape)
    dtype_str = "fp32" if dtype == torch.float32 else "complex64"  # only two dtypes in scope
    key = (op_name, log_n, dtype_str, direction)
    if key in _ROUTING_TABLE and _ROUTING_TABLE[key].get("route_to_cuda", False):
        # First-route logging — once per process per cell.
        if key not in _routing_log_emitted:
            ratio = _ROUTING_TABLE[key].get("triton_cuda_ratio_p50", 0.0)
            log.info(
                "torch_structured: routing %s(log_n=%d, dtype=%s, direction=%s) "
                "to CUDA (Triton/CUDA ratio %.2fx > 1.67x threshold)",
                op_name, log_n, dtype_str, direction, ratio,
            )
            _routing_log_emitted.add(key)
        return True
    return False
```

**Test-fixture concerns:**

Across pytest tests, `_routing_log_emitted` persists (module-level set). If two tests both invoke a routed shape, only the FIRST emits the log message. For tests that verify the logging behavior (e.g., "first call logs, second call doesn't"), a `clear_routing_log` fixture must reset the set:

```python
# tests/conftest.py
@pytest.fixture
def clear_routing_log():
    """For tests that assert on routing-log emission behavior."""
    torch_structured._ops._routing_log_emitted.clear()

```

```python

def test_routing_log_emitted_once_per_cell(caplog, clear_routing_log):

    Subsequent routings of the same shape should NOT re-emit.
```

**Script outline (mirrors the planner-task surface area):**

```python
# scripts/regenerate_routing_table.py
"""Regenerate torch_structured/_routing.json from .planning/phases/07/07-BASELINE.json.

For each (op, log_n, dtype, direction) cell in the baseline, computes
ratio = wall_ms_p50_triton / reference_cuda_p50 and sets route_to_cuda=True
when ratio > 1.67 (= 1/0.60). When reference_cuda_p50 is null (no CUDA
measurement available), falls back to comparing against reference_torch_ref_p50
with a 5× threshold (Phase 7's documented weaker gate).

Run: python scripts/regenerate_routing_table.py
"""
import datetime
import json
import sys
from pathlib import Path

BASELINE = Path(".planning/phases/07-butterfly-multiply-forward-triton/07-BASELINE.json")
ROUTING = Path("torch_structured/_routing.json")
THRESHOLD = 1.0 / 0.60  # = 1.6667

def main():
    rows = json.loads(BASELINE.read_text())["rows"]
    rules = {}
    for row in rows:
        ratio = None
        if row.get("reference_cuda_p50"):
            ratio = row["wall_ms_p50"] / row["reference_cuda_p50"]
            route = ratio > THRESHOLD
        else:
            # Fallback to torch-ref with a 5× threshold (Phase 7 doc).
            ratio = row["wall_ms_p50"] / row["reference_torch_ref_p50"]
            route = ratio > 5.0
        key = f"{row['kernel']}::{row['log_n']}::{row['dtype']}::{row['direction']}"
        rules[key] = {"triton_cuda_ratio_p50": round(ratio, 4), "route_to_cuda": route}

    output = {
        "schema_version": 1,
        "generated_at": datetime.datetime.now(datetime.timezone.utc).isoformat().replace("+00:00", "Z"),
        "generated_from": str(BASELINE),
        "threshold_ratio": THRESHOLD,
        "rules": rules,
    }
    ROUTING.write_text(json.dumps(output, indent=2) + "\n")
    print(f"Wrote {ROUTING} with {len(rules)} rules; {sum(1 for r in rules.values() if r['route_to_cuda'])} marked route_to_cuda")
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

**LANDMINE — the script must NOT auto-run on every test or CI build.** It's an explicit, hardware-dependent regeneration. Document in the docstring: "Run when GPU hardware changes; the resulting JSON should be committed and reviewed."

## §10. `make_linear` + `LRU` test patterns

**Findings (verified against `torch_structured/factory.py` and `torch_structured/recurrent/lru.py`):**

**`make_linear` signature CORRECTION:** CONTEXT.md states `make_linear(in_size=256, out_size=256, structure='butterfly')` — **this is wrong**. The actual signature is:

```python
make_linear(kind: str, in_features: int, out_features: int, *, bias: bool = True, **kwargs) -> nn.Module
```

`kind` is positional (first arg), and parameter names are `in_features` / `out_features` (NOT `in_size` / `out_size`). Correct call:

```python
m = make_linear("butterfly", 256, 256)
# Returns a _ButterflyLinear wrapping Butterfly(256, 256, bias=True).
```

**LRU constructor:** signature is `LRU(input_size, hidden_size, num_layers=1, bias=True, batch_first=False, ...)`. To use a Butterfly-backed projection: `LRU(input_size=64, hidden_size=128, kind='butterfly')` — the `kind` kwarg sets both `kind_B` and `kind_C` to `'butterfly'`. To bypass complex pin: `LRU(input_size=64, hidden_size=128)` defaults to `kind='dense'`.

**Recommended Phase 9 09-01 tests:**

## §13. Public API regression detector pattern (COMPAT-01)

**Recommendation:**

Use **`inspect.signature` snapshotting** — the most maintainable, version-stable pattern.

```python
# tests/test_phase9_integration.py
import inspect

# Hardcoded reference signatures captured from v1.1 release.
# When you ADD a new positional argument, this fails — that's correct;
# adding a positional arg is a breaking change. Use **kwargs for additions.
_V1_1_BUTTERFLY_INIT_SIG = (
    "(self, in_size, out_size, bias=True, complex=False, "
    "increasing_stride=True, ortho_init=False, init=None, nblocks=1)"
)

def test_public_api_butterfly_init_signature():
    """COMPAT-01 — Butterfly.__init__ signature unchanged since v1.1."""
    sig = inspect.signature(Butterfly.__init__)
    assert str(sig) == _V1_1_BUTTERFLY_INIT_SIG, (
        f"COMPAT-01: Butterfly.__init__ signature changed.\n"
        f"  v1.1: {_V1_1_BUTTERFLY_INIT_SIG}\n"
        f"  now:  {sig}\n"
        f"  Adding positional args is a breaking change. Use **kwargs."
    )

def test_public_api_butterfly_attributes():
    """COMPAT-01 — Butterfly instance attributes unchanged."""
    m = Butterfly(in_size=16, out_size=16, bias=True, complex=False)
    expected_attrs = {
        "in_size", "out_size", "log_n", "n", "nstacks", "complex",
        "increasing_stride", "init", "nblocks",
        "twiddle", "bias",

    actual_attrs = {k for k in dir(m) if not k.startswith("_")}
```

## Common Pitfalls (Phase 9–specific)

### Pitfall 1: nn.Module surface bypasses `_ops` dispatcher
**What goes wrong:** `Butterfly(...).forward(x)` under `BACKEND=triton` executes the C++ op (legacy), not the Triton op.
**Why it happens:** `from .multiply import butterfly_multiply` binds the wrapper at import time; the wrapper calls `torch.ops.torch_structured.butterfly_multiply` (C++) directly, not via `_ops`.
**How to avoid:** Resolve §0 by rewriting `torch_structured/butterfly/multiply.py:27-30` to delegate to `_ops.butterfly_multiply` (Option A).
**Warning signs:** All `torch.compile(Butterfly(...))` tests pass green AND the SC#4 monkey-patch test ALSO passes — because the monkey-patch test calls `_ops.butterfly_multiply` directly, not through the nn.Module.

### Pitfall 2: FSDP2 `fully_shard` silently shards `twiddle` in PyTorch 2.6
**What goes wrong:** No exclusion API in 2.6 FSDP2; `twiddle` gets sharded; forward produces garbage.
**Why it happens:** `ignored_params` is in main but NOT in 2.6.
**How to avoid:** Use FSDP1 (`FullyShardedDataParallel(model, ignored_modules=[...])`) for PyTorch 2.6 compatibility (COMPAT-05).
**Warning signs:** `test_fsdp_butterfly_smoke` passes but loss diverges across ranks at log_n ≥ 3.

### Pitfall 3: `fullgraph=True` misses backward-only graph breaks
**What goes wrong:** A graph break in `_backward` callback only surfaces when `.backward()` is called.
**Why it happens:** `fullgraph=True` traces the forward; backward is AOT'd at trace time but executes at backward time.
**How to avoid:** Always include `.backward()` in the test body — not just forward.
**Warning signs:** Test passes the forward part (`m_compiled(x)`); fails at `loss.backward()`.

### Pitfall 4: `do_bench` measurement compares apples-to-oranges across harnesses
**What goes wrong:** Custom-harness CUDA p50 and `do_bench` Triton p50 in the JSON differ by 5–15% due to warmup-time vs warmup-iterations definitions.
**Why it happens:** `do_bench` `warmup=25` is 25 MILLISECONDS; custom harness `warmup=10` is 10 ITERATIONS.
**How to avoid:** Either rewrite the entire harness on `do_bench` (Option B in §5) OR cross-calibrate the two at one cell and document the ~10% margin.

### Pitfall 5: `torch.use_deterministic_algorithms(True)` raises spurious errors
**What goes wrong:** `set_deterministic` test fails with `RuntimeError: cublas determinism requires CUBLAS_WORKSPACE_CONFIG=...`.
**Why it happens:** PyTorch's global deterministic mode requires env var for CUDA matmul/bmm.
**How to avoid:** Set `CUBLAS_WORKSPACE_CONFIG=:4096:8` in the test fixture's env OR use `warn_only=True`.

### Pitfall 6: Routing table read at module import bakes the hardware bias
**What goes wrong:** A user on Ampere installs the wheel containing `_routing.json` baked on Ada — wrong routing decisions on Ampere.
**Why it happens:** Static routing table is hardware-dependent.
**How to avoid:** Document the `scripts/regenerate_routing_table.py` invocation in README. Recommend users regenerate on their hardware OR accept the dev-host bake's defaults (close enough on similar-vintage GPUs).

### Pitfall 7: `pytest -m multigpu` runs ALL tests if marker not registered
**What goes wrong:** Conftest doesn't register `multigpu` → `pytest -m multigpu` runs nothing AND emits a warning. Or worse: runs everything if filter syntax is misread.
**How to avoid:** Register in `tests/conftest.py:pytest_configure` (extend the existing `slow` registration). Always test the marker selection locally before relying on it in CI.

### Pitfall 8: `register_fake` shape inference under view_as_real complex64
**What goes wrong:** Phase 7's `_butterfly_multiply_fake` returns `torch.empty(batch_size, nstacks, output_size, dtype=input.dtype)` — the `dtype=input.dtype` carries the complex64 vs fp32 type correctly. But if a user passes a complex tensor that's been view_as_real'd in user code, dtype is fp32 and the shape inference returns an fp32 fake — but the actual kernel produces complex64 output. Inconsistency between fake (fp32 shape) and real (complex64 shape) causes `torch.compile` to compile against the wrong dtype.
**How to avoid:** The view_as_real round-trip is INSIDE the `triton_op` wrapper (per Phase 7+8). User-facing input is `torch.complex64`. Fake input is `torch.complex64`. Fake output is `torch.complex64`. The boundary stays at the wrapper. This is already correctly designed; the pitfall is in NOT regressing this design when touching `op.py`.
