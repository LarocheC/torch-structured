<objective>
Make `torch_structured` cleanly publishable to PyPI as a pure-Python `py3-none-any` wheel. Triton is JIT, so the default install needs no compiled `.so`; the legacy CUDA C++ extensions become opt-in via `FORCE_CUDA=1`.

Purpose: Today `pip install torch-structured` fails on a stock machine because `setup.py` compiles C++/CUDA extensions on every install (needs torch + ninja + compiler + `--no-build-isolation`). This task produces a clean buildable package and verifies the artifacts locally.

Output: Gated `setup.py`, corrected + version-bumped `pyproject.toml`, graceful extension loading, finalized CHANGELOG, and a locally verified `py3-none-any` wheel.

PREP ONLY — this plan MUST NOT run `uv publish` or `twine upload`. Verification ends at `uv build` + artifact inspection.

  <name>Task 1: Gate CUDA extension build behind FORCE_CUDA=1 and make import graceful</name>
  <files>setup.py, torch_structured/butterfly/__init__.py</files>
  <action>
Two coordinated changes so the default build is pure-Python AND the package imports
without any compiled `.so`.

(A) setup.py — change the DEFAULT to compile nothing. Currently `get_extensions()` returns
extensions whenever `torch.cuda.is_available()`. Change the gate so extensions are built
ONLY when the user explicitly opts in with `FORCE_CUDA=1`. Concretely: in `get_extensions()`,
return `[]` unless `os.getenv("FORCE_CUDA", "0") == "1"` (keep the existing `BUILD_DOCS`
early-return). When FORCE_CUDA=1, build the CUDA variants (with_cuda=True). Preserve the
existing FORCE_CPU env var so a user can do `FORCE_CUDA=1 FORCE_CPU=1` to compile the
CppExtension (CPU) variant of the ops if they want a non-CUDA compiled build; route that
through the existing `_with_cuda()` logic. Net behavior: no env vars set -> ext_modules is
empty -> setuptools emits a pure-Python `py3-none-any` wheel and never touches nvcc/the C++
compiler. Move the `import torch` and `from torch.utils.cpp_extension import ...` so they
only execute on the FORCE_CUDA path (so a default build does not even require torch to be
importable at build time — supports dropping torch from build-system.requires in Task 2).
Keep `cmdclass={"build_ext": BuildExtension...}` only on the compiled path.

(B) torch_structured/butterfly/__init__.py — make extension loading non-fatal. The eager
`_load_extension('_version')` / `_load_extension('_butterfly')` calls (lines 38-39) plus
`check_cuda_version()` (line 66) must NOT raise when the `.so` files are absent (the normal
state for a pure-Python wheel). Change `_load_extension` so a missing extension does NOT
raise `ImportError` — instead emit a single low-noise `warnings.warn(..., UserWarning)` (or
log at debug level) explaining that the compiled CUDA backend is unavailable and the
Triton/pure-PyTorch backend will be used, then return without registering the op. Guard the
`_load_extension('_version')` / `_load_extension('_butterfly')` calls and `check_cuda_version()`
so that when `_version`/`_butterfly` are not loaded, `check_cuda_version()` is skipped (it
calls `torch.ops.torch_structured.cuda_version()` which only exists if `_version` loaded).
Rationale (already verified): `_ops._has_cuda_legacy()` returns False when the op isn't
registered, so the resolver transparently falls back to triton/torch — no further wiring
needed. Do NOT change `_ops.py`.
  </action>
