# Quick Task 260709-ew0

## Problem

`_butterfly_backward_kernel` computes its per-stage `LOG_STRIDE_*` / `STRIDE_*`
`tl.constexpr` values **inside** the `@triton.jit` body using the Python
`max(...)` builtin and a `... if ... else ...` ternary (op.py:1090-1100). On
Triton **3.3.1** the front-end can no longer evaluate these builtins/ternaries
in constexpr context and raises `ValueError('Did you forget to add @triton.jit ?')`
at the `1 << LOG_STRIDE_0` line. (Triton 3.7.0 still compiles them — the bug is
a 3.3.x-specific front-end regression.)

Every input to those expressions (`group_start`, `counter_count`,
`cur_increasing_stride`, `log_n`) is already known on the **host** at the launch
site, so the computation can be hoisted out of the kernel entirely — sidestepping
the front-end fragility on any Triton version. This mirrors how `tile_n` /
`num_warps` are already host-computed.

## Task 1 — Hoist STRIDE computation to the host

**Files:** `torch_structured/_triton/butterfly/op.py`

**Action:**
1. Add `STRIDE_0: tl.constexpr, STRIDE_1: tl.constexpr, STRIDE_2: tl.constexpr`
   to the `_butterfly_backward_kernel` signature.
2. Remove the in-kernel `if INCREASING_STRIDE: LOG_STRIDE_* = max(...)/ternary`
   block and the `STRIDE_* = 1 << LOG_STRIDE_*` lines. Keep `IDX_0/1/2`
   (plain `STAGE_START + k`, which the forward kernel already uses safely).
3. At the backward launch site (the `for group_start` loop), compute
   `stride_0/1/2` in plain Python (mirroring the old formula, with `max(...,0)`
   clamps for the unused slots so `1 << negative` never fires), and pass them as
   `STRIDE_0=/STRIDE_1=/STRIDE_2=`.

**Verify:** `scratchpad/sweep.py` reports the same "OK configs: 40" (forward +
backward parity vs `_torch_ref.butterfly.butterfly_multiply_torch`) as the
pre-change baseline; the `_butterfly_kernel` forward is untouched.

**Done:** Sweep passes 40/40; `import torch_structured` clean; no `max()`/ternary
remains in any `@triton.jit` body in op.py.
